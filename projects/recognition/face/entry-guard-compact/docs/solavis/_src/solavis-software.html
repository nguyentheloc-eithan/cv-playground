1. Scope and product lines

This document is the software design for Solavis. It turns the requirements in SOL-SRS-001 into components, interfaces, data and tests. It is written for the software and firmware team.

Product 1: Solavis Camera (MVP)

Our camera plus subscription. Firmware, cloud, customer app and admin console. Built first.

Product 2: Solavis Platform (later)

Our software sold alone. Customers connect cameras they already own through an on-site agent. Same cloud, same apps.

The rule for the whole team

Build the MVP so that a Solavis camera is just one kind of source. Anything that sends face crops to the device API is a source. Do not put camera-specific assumptions into the cloud, the data model or the recognition code. Section 12 lists what to do now and what to build later.

3. Source abstraction

This is the most important design decision for the two product lines. Every camera is a row in sources. The API and the recognition worker work with sources and never with camera models.

Source typeProductProduces crops byCapabilities
solavis_camCameraFirmware on the camerapir, imu, compass, reed, night_light, ota, solar, lte
agent_rtspPlatformAgent reads an RTSP streamstream_status, view_check
agent_onvifPlatformAgent finds the camera by ONVIF and reads its stream and eventsstream_status, view_check, onvif_motion
uploadBothManual image upload, for tests and toolsnone
  • One input contract. A crop with source_id, time, optional quality hints and optional extra frames. The worker does not know where it came from.
  • Capabilities drive the UI and the rules. The tamper screen appears only if the source has imu or reed. The heartbeat fields differ by type, but the table is the same.
  • Entitlements count sources. A plan limits the number and the allowed types. Usage is metered per source, which later becomes per-channel billing.
  • Agents are devices too. An agent holds a key and talks to the same device API. Each third-party camera it manages appears as a source under that agent.

4. Firmware design

4.1 Security states

stateDiagram-v2
  [*] --> Unclaimed
  Unclaimed --> Mounting: claimed
  Mounting --> Armed: arm command
  Armed --> Service: service window
  Service --> Armed: window ends
  Armed --> Locked: tamper
  Locked --> Mounting: unlock command
  Armed --> Revoked: stolen
  Locked --> Revoked: stolen

The state lives in flash and on the server. The server is the authority. If they differ at check-in, the server wins, except that a camera that locked itself reports it and stays locked until the server says otherwise.

4.2 One wake-up

flowchart TD
  W[Wake] --> R{Reason}
  R -->|PIR| CAP[Capture 3 to 5 frames]
  R -->|Accelerometer or reed| TAM[Tamper check]
  R -->|Timer| CHK[Check-in]
  CAP --> DET{Face found?}
  DET -->|No| SLP[Sleep]
  DET -->|Yes| NET[Connect: Wi-Fi, then 4G]
  NET --> UP[Upload crops and event]
  UP --> SLP
  TAM --> SNAP[Take photo and send tamper alert]
  SNAP --> LCK[Lock and sleep]
  CHK --> NET2[Connect]
  NET2 --> CFG[Send heartbeat, get config and commands]
  CFG --> SLP

4.3 Modules

ModuleJob

detectFace detection on the board. Benchmark first. If too slow, send the best frame and let the server find the face.

4.4 Tamper engine

LayerTriggerDefaultResult
MovedAccelerometer motion for 2 s or more, or tilt change from baseline2 s, 8°Tamper: moved
TurnedHeading change from baseline15°Tamper: turned
RemovedReed switch opens while armedImmediateTamper: removed
Reset or hotspotReset button or hotspot start while armedImmediateTamper: reset
View changedServer compares a small frame with the baselineScore set from pilot dataTamper: view changed or covered
RelocatedBaseline Wi-Fi not seen, or position moved over 50 m3 failed scansTamper: relocated
Gone quietServer misses two check-ins2 × intervalAlert: offline while armed
KnockShort shock below the moved level3 in 10 minutesWarning only
  • On tamper: take a photo, send the alert on the best link, retry until delivered or the battery is low, then set the lock flag, drop the customer's Wi-Fi and the data session, and sleep.
  • Lock flag is written to protected storage before the alert is sent, so a power cut cannot lose it. A reboot reads it and goes straight back to sleep.
  • Unlock comes only as a signed command from the server after the owner's step-up check. The camera never unlocks itself.
  • Arming stores the baseline: gravity vector, heading, Wi-Fi fingerprint, and a reference frame sent to the server.
  • Service window arrives as a command with an end time. The camera ignores tamper until then and returns to armed on its own.

4.5 Flash layout (16 MB, example)

4.6 Rules

  • Never log the device key. Never send it except as the bearer token.
  • Time out every network step. A camera that hangs must reset itself with a watchdog and report the reset reason.
  • Settings come from the server config. No threshold is hard-coded in a way that needs a new firmware to change.
  • Firmware images are signed. The camera accepts a new image only if the signature is valid and the version is newer.

5. Device and customer API

5.1 Device authentication

  • Header Authorization: Bearer <device token>. The server stores only a hash. All calls use TLS.
  • Each request carries X-Time (UTC seconds) and X-Nonce. The server rejects stale times and repeated nonces.
  • Writes carry an Idempotency-Key so a retry after a lost reply does not make a duplicate event.
  • Rate limit per device. Return 429 with a Retry-After.

6. Recognition and evaluators

6.1 Pipeline for one event

sequenceDiagram
  participant S as Source
  participant A as API
  participant Q as Queue
  participant W as Worker
  participant D as Database
  participant N as Notifier
  S->>A: upload-url, then PUT crops
  S->>A: POST events
  A->>A: auth, plan state, limits
  A->>Q: add job
  A-->>S: 202
  Q->>W: take job
  W->>W: quality check, make vectors
  W->>D: search this tenant's vectors
  W->>W: apply thresholds and the two-crop rule
  W->>D: save event and verdict
  W->>N: alert if needed

6.2 Rules

  • Quality gate: reject a crop if the face is under 80 px wide or the sharpness score is under the limit. Log it, do not alert.
  • Search: only vectors with the event's tenant_id. Cosine distance with pgvector. Tenants have at most 500 people, so a plain scan is fast enough.
  • Verdict: known if the best score passes the known threshold. Possible banned match only if at least 2 crops of the event match the same watch list person above the banned threshold, or one crop passes a higher threshold. Otherwise unknown.
  • Model version: store embedding_model on every vector. A model change means re-computing vectors from the stored photos, so keep the registration photos.
  • Thresholds are tenant settings with defaults. Defaults are TBD until pilot data exists.

6.3 Tamper and health evaluator

  • View compare: convert both frames to grayscale at the same size, compare with edge features and a structure score against the baseline, and allow for brightness changes. Report a score, and flag blocked or dark views.
  • Gone quiet: a scheduled job looks for armed sources with no check-in for two intervals, and raises the alert once, then reminds every 15 minutes until acknowledged.
  • Low battery and offline: alert at under 25% battery, and for any source silent over 12 hours.

alter table people enable row level security;

Each request sets app.tenant_id for its database session. Staff routes use a separate role that can read across tenants only through audited functions.

8. Subscription and entitlement engine

def check(tenant, source, action):
    if tenant.state in ("suspended", "closed"):      return deny(402)
    if source.security_state in ("locked", "revoked") \
       and action not in ("tamper", "unlock_check"): return deny(403)
    plan = tenant.plan
    if source.type not in plan.allowed_source_types:  return deny(402)
    if action == "event" and usage(source).events >= plan.monthly_event_cap: return deny(402)
    return allow()
  • States: trial (14 days), active, past due (7 days), suspended, closed (after 30 days suspended, with an export offered first).
  • Daily jobs: end trials, move past due to suspended, delete data of closed tenants, remove photos past the plan's retention.
  • Payment, MVP: staff record a bank transfer and extend period_ends. Automatic payment is a later module behind the same fields.
  • Every check runs on the server for every request, so changed firmware gains nothing.

12. Platform product: what to build now and later

12.1 Do now, inside the MVP

  • Use sources with type and capabilities from the first migration, not a cameras table (ARCH-002).
  • Keep recognition in solavis_core with no web imports, so the agent can use it (ARCH-006).
  • Count usage per source (ARCH-004) and limit by source type in plans (ARCH-003).
  • Version the device API and make it the only way in (ARCH-007).
  • Make the app and API show features by capability (ARCH-005).
  • Keep the view-compare and gone-quiet evaluators source-independent, since third-party cameras need them.

12.2 Build later: the edge agent

flowchart LR
  C1[Customer camera 1] -->|RTSP| AG[Solavis agent]
  C2[Customer camera 2] -->|ONVIF| AG
  AG -->|face crops, device API v1| CLOUD[Solavis cloud]
  CLOUD -->|config, commands| AG
TopicDesign
Where it runsDocker, Linux service, Windows service, Raspberry Pi. A small PC or NVR box on the customer's network.
StreamsReads RTSP (H.264 and H.265). Samples 2 to 5 frames a second, runs motion and face detection locally, and sends crops. No video leaves the site.
DiscoveryONVIF discovery and the camera's own events when available. Manual RTSP address otherwise.
NetworkOutbound HTTPS only. No open ports, no cloud pull from customer networks.
IdentityRegisters with a one-time code, then has its own revocable key. Each camera becomes a source under the agent.
SecretsCamera passwords stay on the agent's machine and are never sent to the cloud.
ReuseThe face detector and quality gate from solavis_core. The existing repository already has IP camera support to learn from.
ChecksStream up or down, frame rate, view changed, covered, gone quiet. No motion or removal sensors.
UpdatesSigned, staged, with rollback.
BillingPer channel (source) per month, on the same usage counters.
Self-hosted editionOptional later: the same containers on the customer's server with a licence server. Not planned for the first release.
