C.2 Name, address and certificate, fully local

Nothing is forwarded and nothing outside can reach the system. That has been the design from the start: no inbound port at all. The domain option I recommended in the first v0.5 draft still contacted outside services (Let's Encrypt and Cloudflare) to get a certificate, so it is dropped. This section is the replacement: a private name, a private DNS answer and a private certificate, all on your PC.

How the tablet finds the PC without a router setting

  1. Private name: guard.internal. The .internal ending is reserved for private networks, so it can never exist on the public internet.
  2. Fixed PC address: router reservation if it has one, otherwise set it in Windows (PowerShell commands further down). Example 192.168.1.200.
  3. Tiny DNS server on the PC: CoreDNS (one small program, run as a Windows service). It answers guard.internal with the PC's address and passes every other name to the router. It only answers questions from your local subnet.
  4. Tablet: in the Wi-Fi network settings choose Advanced, IP settings Static. Enter a free address (for example 192.168.1.201), the router as gateway, DNS 1 = the PC, DNS 2 = the router. Set Private DNS to Off or Automatic.
  5. Mac: add the line 192.168.1.200 guard.internal to /etc/hosts. Nothing else is needed.
  6. Certificate: Caddy's own local authority signs the site certificate (tls internal). Copy only the public file root.crt to the tablet and the Mac and install it (Android: Settings, Security, Encryption and credentials, Install a certificate, CA certificate). Android shows a warning that the network may be monitored; that is expected for a private authority.
# Corefile for CoreDNS on the Windows PC
.:53 {
    bind 192.168.1.200
    hosts {
        192.168.1.200 guard.internal
        fallthrough
    }
    forward . 192.168.1.1          # your router, for every other name
    cache 30
}
  • Trade-off: the PC now also answers DNS on the LAN (port 53). Allow it in the firewall for the local subnet only. If the PC is off, guard.internal does not resolve, which is fine because the system is off too; other websites still work through DNS 2.
  • The root certificate is trusted for all sites on that device. Keep its private key only on the PC (BitLocker on), and never copy it. For stronger protection use a root that is restricted to guard.internal (a name-constrained certificate made with step-ca or OpenSSL, loaded into Caddy). Do this in the hardening week.
  • Passkeys on a private name: Chrome should accept guard.internal as the passkey site name. Confirm this on your exact tablet in the week 1 spike below. Fallback name if it refuses: guard.home.arpa.
  • If the name ever changes, passkeys must be created again. Choose the name once and keep it.

C.5 Login design

What each method really is on the web

MethodHow it worksUsed forNotes

Do not use this system's own face recognition to log in. It is built to recognise residents at a door, not to resist a photo held up to a tablet. The tablet's own biometric is stronger and is already designed for this job.

The admin picks the active methods in Settings, Security: password (fixed), authenticator code on or off, passkey on or off, PIN on or off, auto-lock time, and whether step-up accepts PIN or requires a passkey.

C.6 Data added for security

  • credentials.type is password, totp, passkey or pin. Passkeys store only a public key. TOTP secrets are encrypted with a key kept outside the database.
  • The Auth service turns off PocketBase's own password login for the users collection, so every login goes through it. After a successful login it asks PocketBase for a short access token for that user (the superuser "impersonate" feature), valid for 15 minutes. PocketBase's existing API rules keep working.
  • The browser holds two things: an HttpOnly, Secure, SameSite=Strict session cookie (state, checked by Caddy) and the 15-minute token in memory (identity, checked by PocketBase). Nothing is stored in localStorage.

C.8 Caddy gates

# sketch, check with: caddy validate
(gate_session)  { forward_auth 127.0.0.1:8002 { uri /auth/verify?level=session  } }
(gate_unlocked) { forward_auth 127.0.0.1:8002 { uri /auth/verify?level=unlocked } }
(gate_stepup)   { forward_auth 127.0.0.1:8002 { uri /auth/verify?level=stepup   } }

guard.internal {
    tls internal                              # local certificate authority, no outside service

    @pbadmin path /_/*
    respond @pbadmin 404

    handle /auth/* { reverse_proxy 127.0.0.1:8002 }

    @files path /api/files/*
    handle @files { import gate_unlocked
                    reverse_proxy 127.0.0.1:8090 }

    @writes {
        method POST PUT PATCH DELETE
        path /api/collections/*
        not path /api/collections/events/*     # marking an alert reviewed needs only Session
    }
    handle @writes { import gate_stepup
                     reverse_proxy 127.0.0.1:8090 }

    handle /api/* { import gate_session
                    reverse_proxy 127.0.0.1:8090 }

    @engine_sensitive path /engine/live.jpg /engine/people/* /engine/models/*
    handle @engine_sensitive {
        import gate_stepup                     # tune per route: live.jpg needs only Unlocked
        reverse_proxy 127.0.0.1:8001 { flush_interval -1 }
    }
    handle_path /engine/* { import gate_session
                            reverse_proxy 127.0.0.1:8001 }

    header {
        Strict-Transport-Security "max-age=31536000"
        Content-Security-Policy "default-src 'self'; img-src 'self' blob: data:; connect-src 'self'; frame-ancestors 'none'"
        Permissions-Policy "camera=(self), microphone=(), geolocation=()"
        X-Content-Type-Options nosniff
        Referrer-Policy no-referrer
        Cache-Control "no-store"                 # for API and auth routes; static files may cache
    }

    handle {
        root * C:/entryguard/web
        try_files {path} /index.html
        file_server
    }
}

The engine and the Auth service talk to PocketBase directly on localhost, so they never pass these gates. Because of that, bind every internal service to 127.0.0.1 only.

Honest limits. This gives you the same login ideas as a banking app (biometric unlock, PIN, step-up, device list, lockout, alerts). A website cannot do what a native app can: it cannot detect a rooted tablet, cannot pin the certificate, and cannot hide the screen from screenshots. Physical access to the PC, and an unlocked tablet in someone's hand, remain your main risks. Keep the tablet's own screen lock on.

Recovery command, run only on the PC: eg auth reset-admin prints a one-time link valid for 10 minutes, then forces password, authenticator and passkey setup again.

B.4 Windows PC setup recipe

  1. Check the hardware: CPU with AVX2, at least 4 cores, 8 GB RAM (16 GB is better), SSD, Windows 10 22H2 or Windows 11. Note which Windows version you have.
  2. Install WSL2 and Ubuntu 22.04 (wsl --install -d Ubuntu-22.04), then enable systemd so Docker starts by itself.
  3. Install Docker Engine inside Ubuntu (not Docker Desktop). Run PocketBase and MinIO with the compose file from section A.7, without the Caddy service.
  4. Install Caddy for Windows, run it as a service (WinSW or NSSM), and run caddy trust once.
  5. Set a fixed address: a DHCP reservation in the router for the PC.
  6. Windows firewall: allow inbound 443 only, only on the private network, only from the local subnet.
  7. Install the engine: Windows Python with uv for a USB camera, or inside Ubuntu for an RTSP camera.
  8. Keep it running: disable sleep, auto-login, BIOS setting "restore after power loss: on", pause Windows Update restarts outside active hours, scheduled task that starts WSL at boot.

A.4 Vector search without a vector database

PocketBase has no vector index. At building scale you do not need one. The engine loads all enrolled embeddings into one NumPy matrix at start-up. Search is a single matrix product on unit-length vectors.

# adapters/index/memory_pb.py (sketch)
class MemoryPbIndex:                       # implements IdentityIndex
    def __init__(self, pb, space_id):
        self.pb, self.space = pb, space_id
        self.reload()

    def reload(self):                      # called at start and on PocketBase realtime change
        rows = self.pb.list("embeddings", filter=f'space="{self.space}"')
        self.ids = [r["person"] for r in rows]
        self.mat = np.stack([decode_b64_f32(r["vec"]) for r in rows]) if rows else np.zeros((0, 512), np.float32)

    def search(self, vec, space_id, k=3):
        sims = self.mat @ vec               # cosine, vectors are L2 normalised
        top = np.argsort(-sims)[:k]
        return [(self.ids[i], float(sims[i])) for i in top]
  • 5,000 vectors of 512 numbers is about 10 MB and a search takes about 1 ms.
  • The engine subscribes to PocketBase realtime on embeddings, so a new person is searchable within a second, no restart.
  • Because the index is a port adapter, you can later replace it with FAISS or pgvector without touching the pipeline.
  • Embeddings are stored as base64 text in PocketBase and are readable only by the engine service account, never by a browser.

0.3 Important issue: how "in" and "out" are known

One camera facing people who walk in sees their faces only when they enter. When they leave, the camera sees the back of the head and cannot identify them. To log both in and out reliably you need two cameras, one for each direction. The data model and engine handle this from the start: every camera has a direction (in or out) and every event stores its camera and direction.

1. Executive summary

What you build: a service that reads the entrance camera stream, finds faces, checks each one against a list of enrolled residents, and raises an alert when a person is unknown. You do not need to train a model from scratch. Modern pretrained face models already reach very high accuracy. "Training" in this product means enrolling each resident with a few photos. Fine-tuning a model is an optional later step if measured accuracy at your door is not good enough.

Key design idea: every AI step (detect, align, embed, liveness, track, search) sits behind a small fixed interface called a port. Each model is an adapter that implements the port and is chosen by a config file. You replace a model by adding one adapter file and changing one config line. The rest of the system never changes.

2. Privacy and legal (read before buying a camera)

Face data is biometric data. In most countries it is sensitive personal data. In Vietnam, Decree 13/2023 on personal data protection applies. In the EU, GDPR applies. Rules differ, so confirm with a local lawyer before you go live. The points below are design requirements, not legal advice.

  • Written consent from every resident before enrollment. Store the consent record (who, when, version of text).
  • Notice sign at the entrance saying a camera with face recognition operates there, and who to contact.
  • Minimisation: store embeddings (numbers) and a few enrollment photos only. Do not store video continuously. Save a snapshot only when an unknown person triggers an event.
  • Retention: delete unknown-person snapshots after 30 days by default. Delete a resident's data within 7 days of move-out.
  • Visitors and delivery staff are not enrolled. The system must treat "unknown" as "needs attention", never as "criminal". Alerts say "unrecognised person", not "intruder".
  • Access to data limited to named admins, with an audit log of every view and export.

Ports are small Protocol classes. Data crossing a port uses plain dataclasses and NumPy arrays, never library-specific objects.

# engine/ports.py
from dataclasses import dataclass
from typing import Protocol, Sequence
import numpy as np

@dataclass(frozen=True)
class Face:
    box: tuple[float, float, float, float]      # x1, y1, x2, y2 in pixels
    score: float                                # detector confidence 0..1
    landmarks: np.ndarray                       # shape (5, 2): eyes, nose, mouth corners

@dataclass(frozen=True)
class ModelInfo:
    kind: str            # "detector" | "embedder" | "liveness" | "tracker"
    name: str            # e.g. "scrfd_2.5g"
    version: str         # e.g. "1.0.0"
    sha256: str          # file checksum
    embedding_dim: int | None = None
    space_id: str | None = None   # embedders only: vectors are comparable only inside one space

class FaceDetector(Protocol):
    info: ModelInfo
    def detect(self, image_bgr: np.ndarray) -> Sequence[Face]: ...

class FaceEmbedder(Protocol):
    info: ModelInfo
    def embed(self, aligned_rgb_112: np.ndarray) -> np.ndarray: ...   # L2-normalised float32

class LivenessChecker(Protocol):
    info: ModelInfo
    def score(self, image_bgr: np.ndarray, face: Face) -> float: ...  # 1.0 = real

class Tracker(Protocol):
    info: ModelInfo
    def update(self, faces: Sequence[Face], frame_idx: int) -> list[tuple[int, Face]]: ...

class IdentityIndex(Protocol):
    def add(self, person_id: str, vec: np.ndarray, space_id: str) -> None: ...
    def search(self, vec: np.ndarray, space_id: str, k: int = 3) -> list[tuple[str, float]]: ...
    def remove_person(self, person_id: str) -> None: ...

class Notifier(Protocol):
    def send(self, title: str, body: str, image: bytes | None) -> None: ...

class Actuator(Protocol):              # phase 2
    def open_door(self, reason: str, seconds: int) -> None: ...

6.4 Rules that keep models swappable

  1. Embedding spaces are not interchangeable. Vectors from model A and model B cannot be compared. Every stored vector carries a space_id. Search filters by the active space.
  2. Keep the original enrollment photos (encrypted at rest) so a new embedder can re-index everyone with eg models migrate. Without photos you would have to re-enroll every tenant.
  3. Thresholds belong to a model. Store thresholds per space_id. A new embedder starts with calibrated thresholds from the benchmark command, not the old ones.
  4. Normalise at the boundary. Every embedder returns an L2-normalised float32 vector, so cosine similarity is a dot product regardless of model.
  5. Contract tests. One shared test suite runs against every adapter: output shape, dtype, determinism, handles a 0-face image, handles a tiny face.
  6. Record versions on events. Every event stores detector, embedder and liveness names, so you can explain an old decision after a swap.

MVP: no training. Use pretrained detector and embedder. Collect measurements first. If the benchmark on your entrance footage shows too many errors, address them in this order: (1) fix the camera angle and light, (2) improve enrollment photos, (3) tune thresholds, (4) swap to a stronger pretrained model, (5) only then consider fine-tuning on your own consented data. 7.3 Decision policy

Per-frame results are noisy. The policy combines up to N frames of one track, then decides once.

  1. Collect candidate frames while the track is alive; keep the 5 best by quality score (sharpness x size x frontalness).
  2. If any of the top frames fails liveness (score below threshold in at least half): decision spoof.
  3. For each top frame, take best match. Average the score per person. Take the person with the highest mean and at least 2 agreeing frames.
  4. Mean score at or above accept_threshold: resident.
  5. Mean score below reject_threshold: unknown.
  6. Otherwise: uncertain. Wait for more frames up to max_wait_seconds, then log as uncertain and send a low-priority notice.
  7. No usable face in the whole track: no_face, no alert.

Starting thresholds (0.45 / 0.35 cosine for ArcFace) are placeholders. Calibrate with the benchmark command on your own entrance footage before trusting them.

10.1 Metrics

  • TAR @ FAR: true accept rate when the false accept rate is fixed (report at 0.1% and 0.01%).
  • FRR: residents wrongly called unknown. This drives false alerts.
  • Spoof APCER/BPCER: attacks accepted, real users rejected.
  • Latency: p50 and p95 per stage and end to end.
  • Alert precision: share of unknown alerts that were truly unknown people.

10.2 Building the site test set

  1. Record 2 days of entrance video (with notice posted and consent from residents).
  2. Label tracks manually: person id or "visitor". Aim for at least 20 residents and 30 non-residents (staff, couriers, volunteers).
  3. Include day, night, rain, masks, glasses, hats, phone in hand, group of 3 entering together.
  4. Split by person into calibration and holdout sets. Pick thresholds on calibration, report on holdout.

11. Hardware and camera placement

Camera

  • PoE IP camera, 4 MP, RTSP, wide dynamic range (WDR), IR optional
  • Lens 2.8 to 4 mm, depending on door width
  • Mounted 1.6 to 2.0 m high, looking along the walking path, not across it
  • Face width at the decision point at least 120 px
  • No strong backlight (glass door facing the sun). If unavoidable, add a lamp on the face side
  • Use a PoE switch and a fixed IP address

Compute (pick one)

  • Budget CPU: mini PC with Intel i5 or newer, 16 GB RAM, SSD. Runs 1 camera with MobileFaceNet or ArcFace.
  • Better: NVIDIA Jetson Orin Nano or a PC with an entry GPU. 4+ cameras, bigger models.
  • Development: a Mac with Apple Silicon works with the CoreML provider.
  • Add a small UPS so power blips do not corrupt the database

16.3 Runbook (short)

  • Many false unknown alerts: check lighting change, lens dirty, camera moved. Look at three snapshots. If residents score near threshold, add 2 new enrollment photos in current conditions.
  • No events at all: /v1/health, check camera state, restart engine, check disk space.
  • Slow: look at stage latency; lower target_fps, use the smaller detector, or enable GPU provider.
  • Tenant moves out: disable, then delete after the retention window; confirm audit entry.

20. Glossary and open questions

TermMeaning
EmbeddingA list of numbers (here 512) that represents a face. Similar faces have similar numbers.
Cosine similarityHow alike two embeddings are, from -1 to 1. Higher means the same person.
EnrollmentAdding a person: store photos and embeddings so they can be recognised.
Liveness / anti-spoofCheck that a face is a real person and not a photo or screen.
TrackOne person followed across video frames, with one id.
FARFalse accept rate: unknown people wrongly accepted.
FRRFalse reject rate: residents wrongly rejected.
TARTrue accept rate = 1 minus FRR.
Port / adapterA port is an interface the core defines. An adapter is a concrete model or service behind it.
Model spaceThe set of vectors made by one embedder; vectors from different spaces cannot be compared.
RTSPStreaming protocol used by IP cameras.
